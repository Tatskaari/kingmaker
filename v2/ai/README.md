# v2/ai: the AI service

Part of [v2](../README.md), the production build. The prototype runs some of the same code: its [architecture overview](../../ARCHITECTURE.md) says where.

The AI service, `kingmaker-ai`, is a stateless HTTP service that does all the model work. The simulation, a SpacetimeDB module, calls it with the working set each request needs, from a scheduled procedure; it answers with data the simulation commits, and streams the GM's words back as they're written through a reducer only it may call. It never reads the simulation's tables, and it's the only part that calls OpenRouter. V0 plays one scene with it (v0-design §5), V5 draws its replies as the prototype does: who says each line, the notes on their marks, and the lines the player might say next (v5-design §3.6), V1 makes the character first (v1-design §3.7), and the whole story crosses from one scene to the next as the prototype's does, and picks a scene up after a fight (story-design §4.4):

| [gm/](gm/) | The GM pipeline, copied from the prototype: the prep and the per-turn note, the director's questions and readings, the GM's voice and its markup, who says each line, every directive's words, the stage manager, the notes on a reply's marks, the suggested lines, and the story they're vetted against | [The GM pipeline](#the-gm-pipeline), below; [gm/golden/README.md](gm/golden/README.md) |

llm/, prompts/ and docs/ are the prototype's too, one copy for both builds. gm/ and service/ are v2's alone: the prototype has its own GM, from which gm/ was copied.

## The one rule

**v2/ai imports only `node:` built-ins, its own files, [v2/shared](../shared/) and [v2/vendor](../vendor/),** never the prototype. v2/shared is the plain TypeScript the AI service shares with the simulation (the requests and answers between them, the scene graph, the world, the rules code), and it imports nothing outside itself but the rules engine's typings, so nothing the prototype imports from here reaches the rest of v2. v2/vendor is the rules engine, which the AI service loads itself to make the build cards it offers (v1-design §3.6). The prototype reaches in, and nothing here reaches out to it. [imports.test.ts](imports.test.ts) holds v2/ai to that, since the prototype's type check wouldn't notice, and [v2/shared's own test](../shared/imports.test.ts) holds v2/shared. A change to either runs the prototype's checks too (moon.yml's sources), since the prototype's type check and tests reach them. So:

- **What a function needs of the game, it's handed.** The docs service takes a view of the game's working set ([docs/types.ts](docs/types.ts)), never the prototype's session, and what disclosure keeps comes back as a value for the game to keep.
- **Where the files are is found or configured, never imported.** The prompts are beside their loader. The lore, and each game's copy of it, are where [docs/config.ts](docs/config.ts) says: by default the repo's `lore/` and `runs/sessions/<game>/docs/`, where the prototype keeps them.

The test reads the code with the TypeScript compiler's parser, so it finds an import however it's written. The parser (the `typescript` package, 7.x) is the one import from outside v2/ai and v2/shared, and only the test may make it, so a build that runs the test needs TypeScript.

v2's other rule, that it copies what it needs of the prototype rather than import it, holds here too: this code is v2's, and it's the prototype that imports it. gm/ is such a copy: each file's first line names its source at 44c6d4a and the edits made.

## How the prototype reaches it

None of the prototype's imports changed. Each old path is still there:

| The prototype imports | What's there now | What it does |
|---|---|---|
| `src/llm/openrouter.ts`, `decide.ts`, `tools.ts`, `fake-openrouter.ts` | A one-line shim | `export *` from [llm/](llm/) |
| `prompt` from `src/runtime/brief.ts` | A re-export | from [prompts/index.ts](prompts/index.ts) |
| `src/lore/docs.ts`, `fronts.ts`, `backstory.ts` | Re-exports | from [docs/](docs/); docs.ts also points each game's copy of the lore at the runtime's session folder, which is where the default puts it too |
| `src/lore/disclosure.ts`, `remember.ts`, `reviews.ts` | Adapters, with the old names and signatures | Each makes the working set from the scene and the session ([src/lore/view.ts](../../src/lore/view.ts), with the runtime's own brief.ts), calls in here, and keeps in the session what disclosure hands back |

The prototype's view reads the session when the docs service asks, not when it's made, as the code always did: disclosure runs alongside a turn's decision, and its second round sees the turn as it stands by then. So the prototype sends every prompt as it did before the move, byte for byte.

There's one copy of each module's state: the call log, the spend, the prompt cache and where the docs are belong to the modules here, whichever path imported them. The static build bundles this folder with the rest of the game, and puts the prompts in `content.json` at `v2/ai/prompts`, where their loader looks.

## The service

```sh
cd v2
KM_AI_TOKEN=<the bearer> KM_AI_MODEL=fake npm run ai     # the stand-in model; KM_AI_GM=canned for no GM at all
KM_AI_TOKEN=<the bearer> npm run ai                       # real models: OPENROUTER_API_KEY, or ~/secrets/kingmaker-dev-openrouter.txt
```

`npm run ai` is `node --no-warnings hosts/ai.ts`: plain node, as the container runs it. [hosts/ai.ts](../hosts/ai.ts) is the one file that reads the environment ([service/config.ts](service/config.ts) has every variable: where it listens, the bearer, the store, SpacetimeDB's URL, database and the service's own token for the stream, the model, the GM, the stream's period, the daily ceiling, the test faults). It prints `[ai] listening on http://127.0.0.1:8787 (…)` once it's up, and a line per request.

| Route | What it does |
|---|---|
| `POST /v1/scenes/open` | The opening: disclosure, then `gm.opening`, streamed to the opening's draft. Answers who's here, the opening and the notes opened. After a boundary the opening picks up from how the last scene ended, as the boundary rewrote it. With `aftermath`, the scene picks up after a fight instead: `gm.aftermath`, streamed the same way, and the stage manager's operations for what it narrated (`ops`, by game key), with no disclosure. With `talk`, a talk with a companion opens (town-design §3.6): their greeting (`gm.talk.opening`), streamed the same way, beside the talk's prep (`talk.sift`, then `talk.plan`), which the answer's `talk` brings back: the facts, the one thing they might tell (a secret on their card, and its route out), how near the surface it starts, what's withheld, and the opening lines |
| `POST /v1/turns/decide` | Disclosure beside `director.before`, read into the turn's decision: the route and its check (rolled by the simulation), a cue, the same push again, earned, daft, out of character, a limit, an answer to an ending on the brink, a roll no route covers (`considered`) and a plan off the graph (`offGraph`); for a character with a build, what the rules resolve (`mechanic`: a spell, a blow, a grab or a shove, a jump, a class feature, a rest), with a second small call for the act's details (`director.mechanic`, `.jump` or `.feature`: the spell, its targets by the world's ids, the weapon, where they act from), unless the act is chosen already (`forced`: the map's menu's act, played as the scene's first turn, town-design §3.4), which asks no mechanic question and no details; on the wind-down only `director.ooc` |
| `POST /v1/turns/reactions` | Everyone who saw the player's violence reacts, before the GM says a word (a turn's `reactions` step, when the decide commit's act hurt someone or set something burning or breaking): the witnesses from the world as the act left it (the cast present and the place's other people, the hurt first, ten at most), then `director.reactions` (fight, flee, raise the alarm, cower, intervene, join the player, unmoved), and the GM's direction for what was decided. No model call when nobody saw it. 20 s |
| `POST /v1/turns/consider` | The GM's ruling on a risky act no route covers, before the reply (a turn's `consider` step, when the decide read `considered` or `offGraph`): `consider` (Luna, no reasoning, cut off at `KM_CONSIDER_DEADLINE_MS`, 12 s), its verdict (a roll and its DC, or a plain yes or no) and the route the simulation rolls; with no ruling in time, the plain check to roll instead (`director.freeform`). 200 either way |
| `POST /v1/turns/reply` | The directives, rebuilt from the decision and what the decide commit did, then `gm.reply` (or `gm.closing`), streamed to the turn's draft |
| `POST /v1/turns/settle` | The stage manager's operations (by game key, at most 16) beside `director.after`, which reads whether the player walked out of the place (`left`, for a character with a build) and what the reply left hanging over them (`threat`, `threat_severity`: someone's blow, or a danger they save against, which lands as their next turn begins); no reading when the reply closed the scene. A talk's has no stage manager (a talk has no world): `director.after` reads its staged secrets too (`guard`), and beside it come the next lines (`talk.suggest`, when the controller has lines suggested); once the one thing they kept back is told, their guard is settled and their memory of telling it is written, once |
| `POST /v1/turns/notes` | The notes on a reply's marks, written from what the player knows: placed on its words, linked, each link with its card. `{ marks: [] }` when there's nothing to note, or the model fails |
| `POST /v1/turns/suggest` | The lines the player might say or do next: screened, judged and mixed, with what was dropped and why. `{ lines: [] }` when the model fails |
| `POST /v1/turns/remember` | The memory reviews of a turn once it's over (a background job): the attention filter (`memory.attend`), then the memories and lore agents it fires (Luna tool loops), writing first-person notes into the game's copy of the lore; the turn's line in its `memory-reviews.jsonl`. A 500 when the attention filter fails, with nothing written |
| `POST /v1/turns/repair` | The background co-GM's review of a turn once it's over (`repair`, Luna at medium effort): notes, whispers, canon, routes and bridging beats, a forward move of the tracker, which the simulation merges at the next turn's start |
| `POST /v1/scenes/boundary` | The boundary after a scene ends (a job, keyed by the ended scene's last turn): what the story still owes the player, traced in the ended scene's world; then `handoff`, `boundary` (the verdict on the scenes it could go to: which still holds, where its prep is out of date, its opening rewritten, the lead, what's owed) and `fronts` at once, each falling back as the prototype's does; `director.presence` for the scene chosen, asked only of its people the hand-off or the adjustments name; and the game's docs, each written once for the boundary (the ending's memory for everyone there, the time between for whoever the lead or an adjustment names, the played scene in the story's index, the fronts doc). Answers the hand-off, the last four moments, the next scene with what's handed on to it, what's still owed (its things by entity key) and what moved in the fronts |
| `POST /v1/characters` | Character creation's builds, each made legal by the rules engine with its card: three for a concept (`offer`, `rules.builds`), the model's one (`pick`, `rules.build`), or the player's own picks (`own`: no model; a pick off the SRD's lists is refused in its words), with the lists to pick from |
| `POST /v1/backstories` | The backstory, for the world in campaign.json's `creation`: a draft (`backstory.draft`), the player's notes worked in (`.work`), the lore check (`.check`), what it says of them (`.traits`) |
| `PUT /v1/campaigns/{campaign}/{version}` | A campaign version's words: every file of its folder, each scene loaded with them first, its `creation` block and its `vocabulary.json` checked |
| `POST /v1/looks` | How things the story made look on the map (town-design §3.7): `look.invent` (Luna, no reasoning) for a batch of twenty, an `Invention` per key it answers (a glyph from the menu, a Nerd Font icon, a palette colour, how it moves, light, being, group, material); a key it left out, or a batch whose call failed, has none. 30 s |
| `GET /v1/health` | `{ ok, model, gm, campaigns, token, budget }` with no bearer needed (`budget`: the daily ceiling and today's spend); `?deep=1` adds `stdb`, from calling the module's `service_ping` as the service |

The requests and answers are [v2/shared/protocol/ai.ts](../shared/protocol/ai.ts)'s. Before any model is asked, [service/requests.ts](service/requests.ts) checks a think's request has what its endpoint reads (the turn's scene, line and transcript, the GM's bookkeeping, the world's rows, the sheet; the open's scene and stream; the reactions' act; the reply's decision and outcome; the settle's reply, lines and settled; the consider's read and pending ending, when sent; the turn reviewed by remember and repair), whichever GM answers it, and character creation's (who, the level, the ask or the op, the text): before a kept answer or the daily ceiling is looked at, so a request it can't read is a 400 whatever today's spend.

- **The bearer** (`KM_AI_TOKEN`, the module's `AI_TOKEN`) on every route but health: 401 without it.
- **Answers by key** ([service/server.ts](service/server.ts)). A think's `Idempotency-Key` is its body's `key`: a turn's `<game uid>:s<scene>:t<turn>:<step>` (a turn's later asks for its lines are `suggest-2`, `suggest-3`…), or a creation's `<uid>:c<rev>:<step>` (a creation's uid is the game's to be). The key's step says which endpoint it's for (`STEP_ENDPOINT`); character creation's two serve several steps each. An answer is stored before it's sent; the same POST again is answered from the store with no model call (`X-Km-Replayed: 1`, and "from the store" in the log); a duplicate that comes while the first is still running joins it; the same key with another body is 409 `key_reused`.
- **Errors** are `{ error: { code, message } }`: 400 `bad_request` (unreadable, a key that isn't the header's, the endpoint's or the game's, a request missing what its endpoint reads, an ask or op that isn't its key's step, a campaign not installed, a scene it hasn't got, a campaign PUT whose names, `campaign.json`, `creation` block or `vocabulary.json` it can't read), 401, 402 `over_budget` (below), 403 `key_refused` (OpenRouter turned the key down: its message is the player's words, where the key is changed, `KEY_REFUSED`'s unless the host gives its own, and the game fails the move at once, as for `over_budget`), 409 `other_campaign` or `key_reused`, 413 (a body over 2 MB, or 16 MB for a campaign), 500 `model_failed` (anything the GM throws, after the model client's own retries; character creation's model failing isn't one: its answers say so), 503 `not_ready` while shutting down. The module retries 429 and 5xx and fails the move on the rest.
- **The daily ceiling** ([service/budget.ts](service/budget.ts)): `KM_AI_DAILY_USD`, $5 unless it's set (0 for none), against what the ledger says today's (UTC) calls have cost, read on from where the last read ended. Past it, a think that may call a model is 402 `over_budget` before it runs, and the game fails the move with its words ("The GM has spent today's budget ($5.00): it starts again at midnight UTC, or raise KM_AI_DAILY_USD."); the notes and the lines, jobs beside a turn, are given up instead (the reply unmarked, the moment with no lines). An answer kept by its key is still served, a think already running may go over by its own cost, and own's step and the canned GM, which call no model, aren't stopped. Raise it and restart the service; `/retry` asks again. It's one ledger's: right for one process.
- **The stream** ([service/stream.ts](service/stream.ts)): the reply's words as they're written, posted to `stream_reply` over SpacetimeDB's HTTP API as the service's identity (`KM_STDB_TOKEN`): the first words at once, then at most one post a period (`KM_AI_STREAM_MS`, 200 ms), in order, seq rising, the final words with `done`. Without a token nothing streams, and the answers still work.
- **Each request's model calls** ([service/calls.ts](service/calls.ts)) go through a call context of their own: logged to the game's `calls.jsonl` with the key and the attempt, their costs to the ledger and the answer's `usage`. The memory reviews' tool loops go through it too (`runTools` and `reviewTurn` take the request's `calls`; the prototype calls them without). On the stand-in model (`KM_AI_MODEL=fake`, its options in `KM_AI_FAKE` as JSON: replies, choices (a question's choice, or a list of them: the first one the question offers, as the whole story's recipe ends each scene at the first of its endings), `byName` (the boundary's verdict under `boundary`, the fronts' moves under `fronts`, the notes' writer's answer under `notes`, the co-GM's under `co_gm_notes`, the GM's ruling under `ruling`; character creation's under its schemas' names: `builds`, `build`, `backstory`, `lore_check`, `traits`), `toolCalls` (a tool loop's calls by its first tool: `save_memory` for the memories agent, `search_lore` for the lore agent), `stall` (`["ruling"]` holds the ruling past its deadline), the world bridge's `choices` (`mechanic`, `spell`, `aim_thing`, `aim_<id>`, `target`, `weapon`, `also`, `means_only`, `react_<id>`, `threat`, `threat_severity`: `{"mechanic":"cast","spell":"magic-missile","aim_thing":"hoist-rope"}` casts Magic Missile at the rope on every line), `suggestions` (the suggester's lines, one text a set: several sets go a turn each, as the replies do), `talkSuggestions` (a talk's lines, the same way, apart from a scene's), the town's `byName` (a talk's prep under `talk`, the looks under `looks`) and `choices` (`deepest`, `told_<n>`: the sift's; `guard_<id>`: a staged secret's stage), `handoff` (the hand-off between two scenes: without it, the hand-off is the turn's reply, as any other text), `streamMs`, `decisionDelayMs`, `byNameDelayMs` (`{"notes": 3000}` holds the notes) and `suggestDelayMs`), each request gets a fresh stand-in whose replies begin at the turn's number (a creation's step at its first).
- **The GM** is the pipeline ([service/endpoints/](service/endpoints/)), or with `KM_AI_GM=canned` answers with no model at all ([canned.ts](service/endpoints/canned.ts)): the opening and each reply streamed a word at a time, someone of the cast saying a line in each; a why on that line, linked to them, with their card; the same four suggested lines (two to say, a deed, a risky try); and nothing moving the scene; character creation's offline answers (three builds from the class defaults, no draft, the backstory unchecked, its traits from the player's own words). For bringing a stack up, and for telling the plumbing's faults from the GM's.
- **Stateless.** Nothing of a game outlives its request in memory. Kept between requests, in the stores ([service/stores.ts](service/stores.ts): a folder for V0, [service/folder-stores.ts](service/folder-stores.ts), `KM_AI_STORE`; in memory for a page's or a test's, [service/memory-stores.ts](service/memory-stores.ts), handing each write to whatever its host keeps them in; one contract for both, [service/stores.test.ts](service/stores.test.ts)): the answers by key (swept after a week), each game's call log, memory reviews (`memory-reviews.jsonl`) and copy of the lore, the ledger, and the campaigns as PUT. In memory: an installed version's scenes and its story, read afresh when the version is PUT again, with what the copied code keeps of them (each scene's names, the words any scene might use, the public lore's names), which goes with the story it was kept for; the rules engine and its pack (loaded on the first `/v1/characters`); the prompts, the docs service's registries, how far the ledger has been read, and the requests in flight.
- **Faults, for the tests:** `KM_AI_FAULTS=exit-after-store:<step|any>` ends the process (137) right after it stores such an answer and before it sends it: a turn's `open`, `decide`, `reactions`, `consider`, `reply` or `settle`, the `notes` or the `suggest` beside it (`suggest` covers every ask of a turn's lines), the `remember` or the `repair` after it, the `boundary` after a scene, the `look` of what a turn made, or a creation's `offer`, `pick`, `own`, `draft`, `work`, `check` or `traits`.
- **Shutting down** (SIGTERM, SIGINT): it takes nothing new (503 `not_ready`), gives what's running ten seconds to finish and be sent, and exits 0. So the dev host's `r`, or a host scaling in, loses no answer. Another signal meanwhile changes nothing: under `npm run ai`, one Ctrl+C reaches the service twice (from the terminal, and passed on by npm).

### The container

```sh
podman build -f ai/Containerfile -t kingmaker-ai .      # from v2/
podman run --rm --network=host --userns=keep-id -v ./runs/dev/ai:/data:Z \
  -e KM_AI_LISTEN=127.0.0.1:8787 -e KM_AI_TOKEN -e KM_STDB_URL -e KM_STDB_DB -e KM_STDB_TOKEN -e OPENROUTER_API_KEY kingmaker-ai
```

`node:26.9.0-slim` with v2's package.json (for `"type": "module"`), ai/, shared/, vendor/ (the rules engine, its pack and the SRD's spells) and hosts/ai.ts: the service has no dependencies, so there's no npm install. The store is the `/data` volume, written by the image's `node` user: `--userns=keep-id` makes that the host's own user, so a host folder works as the volume.

## The GM pipeline

The prototype's GM, a step a request (gm-port §5, §6, §8, §9). The copied functions keep their bodies; what changed is what they read. A **TurnView** ([gm/view.ts](gm/view.ts)) is the request as they read the prototype's session: the fields they use, under the same names, built afresh from each request (the GM's bookkeeping, the player from the sheet with the backstory they wrote at character creation, the scene's entries with the player's lines as `player`, the world rebuilt from the place's rows), and after a boundary the story so far as the prototype's session had it (the request's chapters as its `history`, the earlier scenes' entries before this scene's, each with its scene's key, and what the boundary handed on: the adjustments, the rewritten opening, the lead, who's absent, what's been fought, what's owed with its essential from the scene it was placed in), with the later verticals' fields empty. Once there's a story so far, every think's view has the campaign's story on it, so the GM's note of what the player knows names the scenes played by their titles. The settings are the prototype's `v2` approach's: the docs service's memory, the comic tone, no reasoning, the essentials in the prep, Luna's decision mode for the director and Jev for disclosure.

The wind-down: `director.ooc` alone |

| open, after a boundary | as the opening, with `openingDirective`'s second branch: the whole of the opening, as the boundary rewrote it, picked up from how the last scene ended; the prep has the story so far (every hand-off, what play settled there, the last moments) and where the prep is out of date |
| open, an aftermath | `resumeAfterFight`'s middle ([gm/aftermath.ts](gm/aftermath.ts)): `gm.aftermath` with `aftermathDirective`, streamed, then `stageAftermath` (`world.stage`: its operations returned, the player kept in the place) |
| open, a talk | [gm/talk.ts](gm/talk.ts), the prototype's talk.ts: the facts startTalk set (`talkFacts`: where and when, how often, where the story goes, what the companion knew in the story's scenes); `gm.talk.opening` ("Open the talk." and the template's opening) beside `planTalk`: `talk.sift` (which notes are still theirs to tell, and the deepest, held back before the third talk), then `talk.plan` → `prepareTalk` (the `TalkPrep`). No disclosure, as openTalk opens none |
| decide, a talk, or forced | a talk's settings (scenes/talk.ts's approach: no `roll_call`, no `off_graph`, the means only for a route with a social check, no pretending in the limit); `forced`, the menu's act: no mechanic question, no details call, the act the decision's `mechanic` (`rulingOf`) |
| settle, a talk | `afterQuestions` with staging (`guard_<id>` for each of the cast here with a secret, not yet settled) → `readAfter` (`guard`) beside `talkLines` (`talk.suggest`); out is out (`toldIt`, the route `confided` or a guard settled) → `rememberTold` |
| looks | [look/invent.ts](look/invent.ts), the prototype's src/game/look/invent.ts model half: `inventLooks` (`look.invent`), its answers made safe (a glyph by its menu name, a colour or a motion off the lists back to grey and still) |

**People by the game's keys.** A view names people as the copied code does, by the world's ids (the cast by theirs, the place's own people by theirs: `porter`); requests and answers name them by the game's keys (`granary-yard/porter`). A request's markup is mapped in (`localMarkup`, its cards dropped) and every answer's mapped back (`gameMarkup`): who says each line, as it streams and once it's whole, and whom a note links to.

**The story** ([gm/story.ts](gm/story.ts)). What the notes and the lines read of scenes besides the one played (the story's names and places, the words any other scene might use, a played scene's title) the prototype read from its 25 scenes. The AI service has only its campaign's: a scene the campaign installs is read from it, with its place as its world, and each of the rest is a stub from the campaign's `vocabulary.json` (its hook, its ways on, its cast's names, its world's names and its prep as one text). So the vetting is the prototype's: the hanged clerk's story is itself, caerwyn-afternoon, the Rat, wharf-night, the Heron and the King's morning, and the words any other scene might use are the other 19 scenes' prep and the GM's standing instructions. What the copied code keeps of the story (each scene's names, the words any other scene might use, the public lore's names) is kept with it, so a version PUT again (the dev host's `p`) is vetted and linked by its new words. Only the notes, the lines and the GM's ruling read the story (the ruling for the names the player hasn't heard, and never failing on it: a vocabulary that doesn't read leaves the scene's own people), and once there's a story so far every think does (its GM's note of what the player knows names the scenes played, by their titles), so a first scene's own thinks never depend on `vocabulary.json`; the PUT refuses one that doesn't read as the story reads it (the campaign check reads it the same way).

Left out still (gm-port §11, full-gm-design §2.2): the quick co-GM and the lite memory: on a plain turn neither puts a word in the prompt. Staged secrets, talks and a talk's lines are the town's ([docs/town-design.md](../docs/town-design.md) §3.6): only a talk stages secrets, and a scene of the story's prompts are as they were. The boundary and the story so far are the whole story's ([docs/story-design.md](../docs/story-design.md) §4.4): a first scene's prompts are as they were. An exit's effects are the simulation's. Considered rolls, the background co-GM and the memory reviews are the full GM's ([docs/full-gm-design.md](../docs/full-gm-design.md)); spells, blows, the reactions to them and threats are the world bridge's ([docs/world-bridge-design.md](../docs/world-bridge-design.md)), and the suggested lines hear the sheet's spells.

**Prompt parity** ([gm/parity.test.ts](gm/parity.test.ts)) is the acceptance test: on the prototype's own calls, recorded once ([gm/golden/README.md](gm/golden/README.md)), the AI service's GM asks what the prototype's asks, byte for byte for the GM's, the stage manager's, disclosure's, the notes' writer's and the suggester's calls, and question by question for the director's and the judge's; and comes to what it comes to: who says each line as it streams and once it's whole, the notes placed, linked and carded, every field of the vetting, the lines and what was dropped. A second recording has a player with a backstory from character creation ([gm/golden/hanged-clerk-backstory](gm/golden/hanged-clerk-backstory/README.md)): the player's doc and the brief's "who they are" come out as the prototype's (its GM's steps: the notes and the lines with a backstory have no recording of the prototype's).

## Character creation

V1's two endpoints (v1-design §3.7): each step of making a character is a think of its own, a job on the simulation's loop, keyed by the creation's uid and its rev. The simulation keeps the creation; the service makes what each step asks for and keeps nothing of it but the answer by its key.

| Step | Endpoint and ask | What runs | Model calls |
|---|---|---|---|
| `offer` | `/v1/characters`, `{ kind: "three" }` | `threeBuilds` ([rules/builds.ts](rules/builds.ts)): the model's three, each made legal and made by the engine (its card); a class it doubled, or all three when it can't be asked, from the class defaults the concept's words suggest | `rules.builds` |
| `pick` | `/v1/characters`, `{ kind: "one" }` | `pickBuild`: the model's build for the concept, made legal, a Fighting Style fitted to its weapons, and its card | `rules.build` |
| `own` | `/v1/characters`, `{ kind: "own", picks }` | `ownBuild` ([v2/shared/rules](../shared/rules/)): the player's species, class, subclass and background, the rest the class's defaults; a pick off the SRD's lists refused in its words; the lists to pick from, always | none |
| `draft`, `work`, `check`, `traits` | `/v1/backstories`, `{ op, who, text }` | `draftBackstory`, `workIn`, `checkLore`, `finishBackstory` ([docs/backstory.ts](docs/backstory.ts)), for the world in campaign.json's `creation` | `backstory.draft`, `.work`, `.check`, `.traits` |

- **The engine** ([rules/load.ts](rules/load.ts)): the module-ready bundle under plain node, after [the shim](../shared/rules/shim.ts), with its pack and the SRD's spells, handed to v2/shared/rules, which holds the one copy of the rules code the simulation runs too. It loads on the first `/v1/characters` and stays for the process. Nothing is pinned: a card's ids come from the platform's crypto and its clock is real, since the card is shown, not kept (the simulation makes the real character from the build).
- **The model** is asked through the request's own calls, as every think's are, with the prototype's prompts. When it fails, or there's none (`KM_AI_GM=canned`), the answers are the prototype's offline ones, as 200s: the class defaults and a note saying why, settleBuild's fallbacks for the model's one, no draft ("The GM is offline…"), the backstory unchecked with the reason, its traits from the player's own sentences. Only the engine failing is a 500.
- **The backstory reaches the GM**: the sheet the simulation sends has it (`SheetRow.backstory`), the opening writes it into the player's doc before disclosure reads that, and every think's view has it on the player, so the brief says who they are from it.
- **Prompt parity** ([rules/parity.test.ts](rules/parity.test.ts)): each of the prototype's creation calls, recorded once from `44c6d4a` ([rules/golden/README.md](rules/golden/README.md), `tools/v2/record-v1-golden.mts`), asked again through the endpoint as the simulation would ask it, on a stand-in told the same answers. Every request body is the prototype's, byte for byte, and what's made of the answers is what the prototype made.

## Changing it, and checking both

A prompt is one file, in [prompts/](prompts/), for both builds. To change one:

1. Edit it here. The prototype reads a prompt once per process, so restart a running game to see it; the background jobs, in processes of their own, read it fresh.
2. The checks offline: `npm test` runs the prototype's tests and v2/ai's (a few hold a prompt's words), and `npm run check` runs CI's checks.
3. What it does is only seen in a model's replies. The prototype's evals, live, before and after: `npm run eval -- --suite reply --approach v2 --samples 3`, then `npm run compare -- runs/evals/<before> runs/evals/<after>`. To try a variant without editing the file, put a file of the same name in a folder and set `KM_PROMPTS_DIR` to it ([evals/README.md](../../evals/README.md)).
4. In play: `npm run scene -- start hanged-clerk --session p1`, then read `runs/sessions/p1/calls.jsonl` for each prompt as it was sent.

v2 sends prompts through the copy in gm/, so a change to a prompt here changes both builds, and the parity test ([gm/parity.test.ts](gm/parity.test.ts)) says whether V0 still asks what the prototype asks. A change to the GM's code in the prototype (src/runtime) doesn't reach v2: copy it into gm/ and re-record the golden calls ([gm/golden/README.md](gm/golden/README.md)). v2/ai's tests run under both builds' `npm test`: v2's (`cd v2 && npm test`) and the prototype's (`node --no-warnings --test 'v2/ai/**/*.test.ts'`, plain node).

The docs service and the model client are changed the same way, with the same checks. In the docs service, keep the working set plain data, and add to [docs/types.ts](docs/types.ts) only what the code uses; the prototype's [view.ts](../../src/lore/view.ts) then makes it from the session.

## What isn't here yet

The rest of the AI API is still the prototype's, and v2 builds it a vertical at a time:

- **the rest of the GM pipeline:** V0's, V5's, the full GM's and the whole story's part is in gm/ (a copy: the prototype's own is still in src/runtime and src/world/stage.ts); the voices of the `actors` approaches (a narrator and each character's own voice), the quick co-GM, and a boundary previewed without moving on (the zoo's boundary desk) are the prototype's only;
- **the other model work:** the decider's reading of a line typed in a fight and the GM's line after it, with fight.md (src/game/combat); the world scribe's update script after a scene, with scribe.md (src/world/scribe.ts); a place's plan, compiled into a map (src/game/map/generate); skill modifiers from the concept when there's no build, and the sheet a character-creation scene writes from its conversation (src/runtime/engine.ts);
- **stores for a stateless host:** the service's stores are behind interfaces, but V0's are a folder, and the docs service reads and writes each game's copy of the lore as files (see below).

The evals call the model too (src/eval and evals/: the judge and the simulated players, with judge.md and player-sim.md from here). They check the AI API's work, and aren't part of it.

When a part moves, it can come the way these did: one copy here, and an adapter at the prototype's old path.

## Known gaps and sharp edges

- **A scene's own turn numbers.** An earlier scene's entries come numbered by that scene's turns, as the rows keep them (the prototype's were the session's). Where the copied code looks a player's line up by its number alone (the notes' writer citing "turn 3"), an earlier scene's line of the same number can be taken for this scene's; a deed's link names its scene, so its card is right.
- **State per process.** The call log's path and the spend are module state, which the service keeps out of by giving each request a call context. Where the docs are is module state too ([docs/config.ts](docs/config.ts)), with one lore root a process: so the service serves one campaign version, the first a request or a PUT names, and another is 409 `other_campaign` until it restarts. The docs service's registry of who has lore is per lore root, so a version re-installed with changed lore needs a restart too.
- **Synchronous docs.** The docs service reads and writes each game's copy of the lore synchronously, through a volume (a folder, or docs in memory written behind). That works in one process, a container with a volume, or a browser's worker, but not on a stateless host, where a store per game loaded before a request and committed after it comes first.
- **The old paths are shims.** A branch from before the move that changes `src/llm/*.ts` or `src/lore/*.ts` meets a shim or an adapter there on merge: the change belongs in the file here. Edits to the prompts, the READMEs and the fronts test follow the move on their own. A new prompt from such a branch doesn't quite: git reports a "file location" conflict and puts it in v2/ai/prompts/, where `git add` settles it. (With `merge.directoryRenames` set to false there's no conflict, and it stays in prompts/, which nothing reads, until it's moved with `git mv`.)
- **lore/README.md still names src/lore.** The docs service reads it as lore (a gm doc the review agents can find in a search), so the move left it as it was, and the models read it as they did. Its links reach src/lore's adapters, but the command it gives for the fronts test fails: the test is [docs/fronts.test.ts](docs/fronts.test.ts) now. Nothing stands in for it at the old path, since a file there would stop a merge following the move: a branch's change to the test would meet that file instead of reaching this one. Its paths change with the lore, in a change of its own.
