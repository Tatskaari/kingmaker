The target in one picture

Players’ clients talk only to the simulation. The simulation calls the AI API, and the AI API calls OpenRouter. The campaign is installed into both.

A line in a scene, end to end

  1. t 0.00 sTamsin says a line. It’s a move: a reducer checks it, records it and opens the turn. The commit is the acknowledgement, and it reaches every client at once.
  2. t 0.01 sThe simulation asks the AI API. A procedure reads the turn’s working set in a short transaction, then posts it with nothing locked.
  3. t 0.01 to 0.60 sThe decider and disclosure, at once. Is it a route, a roll, a spell? Which notes does each person present open? Multiple-choice questions, about a third of a second each.
  4. t 0.61 sThe decision is committed. Then the GM is asked for the reply, told exactly what was decided.
  5. t 1.56 sThe first words. The AI API posts the text so far to the simulation about five times a second, and every client watching the scene sees it grow.
  6. t 2.43 sThe reply is final. It goes into the transcript, and Tamsin can type again. The world catches up behind her.
  7. t 2.43 to 5.78 sThe world is settled. The stage manager writes what the reply established as world operations (here, a note on Kell), and the simulation checks each one before it lands.
  8. after the turnMemory. A review job writes what the people present will remember into the game’s documents. Nothing waits for it.

The flow is the design’s (content-server.md, §5, “A line in a scene”). The times are the prototype’s, from a real first turn in the live check of 15 Oct 2026; the hops the split adds cost milliseconds.

The design goals

What the production build keeps, changes and promises.

  1. Engine and data apart

    Drop in a different lore folder, or a git repo, and play it. A scripting API builds custom features without engine changes; the world language the stage manager writes today is the start of it.

    The architecture · The scripting API

  2. Two server-side parts

    The AI API runs the model work and holds the docs and memories, self-contained. The simulation state is stored and changed through SpacetimeDB reducers.

    The architecture · The data

  3. Players’ moves run on the server

    A move with no model call is a SpacetimeDB reducer: transactional and deterministic. A move that needs the AI is a procedure, which can make HTTP requests and commits its own transactions. Clients subscribe to read-only views (SpacetimeDB’s docs).

    Moves

  4. No client-side prediction

    The client shows what the server decided. That keeps it simple, and the slow part, the GM, can’t be predicted anyway.

    The client API

  5. Stateless and scalable

    Each move loads the game, runs and commits with a revision check, so any server can take any move. The first version is one server and four clients. Multiplayer is BG3-style: the player who starts a scene controls it until they hand it off.

    Hosting · BG3-style control

  6. Secrets aren’t a security concern

    The content is public and the game isn’t competitive: a player who reads ahead only spoils their own fun.

    The data

  7. Keep what works

    The presentation code and the agent prompting carry over from the prototype, the prompting above all, which works incredibly well.

How the AI works

Each turn of Kingmaker’s game master is a short pipeline, and every call in it is logged with its prompt, its answer, its latency and its cost.

Small multiple-choice decisions read the moment, each in a third of a second. Ordinary code applies the D&D rules and the world’s physics. One model voices the reply, told exactly what was decided. A second pass writes what the reply established back into the world, in a small language the world checks. Then background agents write down what people will remember. Everything on this page comes from real games, and anyone can open the log behind it.

The AI is the most built part of the target. Written from the code on claude/kingmaker-v2-poc and from games played on 14 and 15 Oct 2026; how far each part has come is in Where we are.

Since 18:03 on 15 Oct, considered rolls are v2’s default. v2 no longer waits for the quick co-GM: when the decider flags an act a roll should settle and no route covers, the GM rules on it before it replies. The games on this page were played before that, so their turns still show the quick co-GM. Considered rolls, where we are.

The order, and why

  1. Merge the co-GM’s notes. A background review from an earlier turn may have left notes or new routes in repair-NNN.json. They’re merged first.
  2. The rules go first. Anything the last reply left hanging lands before the player’s act: a spell’s duration running out, fire spreading (the world’s tick), a blow someone was in the middle of. The GM is told the outcome before anything else, as at a table.
  3. Three things at once: the director’s decision (director.before), disclosure (memory.disclose.<scope>, one call per person present and one for the GM) and the quick co-GM (repair.quick).
  4. The rules settle what’s theirs: a route’s skill check is rolled, a spell or a blow is resolved, and if that was violence, everyone present reacts (director.reactions). Each decision becomes a short paragraph for the GM under “For this reply”.
  5. Off the plan? If the director judged the turn off the scene’s graph, the runtime waits for the quick co-GM until 3 seconds after the turn began. If it opened a route, the turn is decided again with it.
  6. The reply streams (gm.reply), one call to Luna at reasoning none.
  7. After the reply, in parallel: the stage manager (world.stage) writes what the reply established into the world, and the director reads what happened (director.after).
  8. Endings, gear and the save. If the story reached an ending, the scene closes. Gear the story moved changes the character sheet. The session and a snapshot are saved once, at the end.
  9. Background jobs, never waited for: the attention filter and memory agents, and the full co-GM review when it’s due. Their results land in later turns.

Decisions, not free text: the decider’s questions

Almost every judgement in the game is a multiple-choice question, built from the game’s own state and answered with a probability for every option.

The options come from this scene’s routes, this character’s spells, the things within reach, this front’s steps. Each comes with a sentence saying what it means. One call answers all of a turn’s questions at once. That makes a judgement:

  • cheap and fast: about a third of a second, and $0.0004, for a call that asks nine questions;
  • consistent: the same question, worded once in code, every turn;
  • checkable: the choice can only be one of the options, and the probability says how sure it was.

The runtime then acts only on a confident read, and the bar rises with the cost of a mistake.

The director is Luna’s decision mode, through OpenRouter’s Decisions API. Jev, TypeSafe’s decision model, answers the many small yes-or-no questions of disclosure and the attention filter. Both take named options in and give a choice with probabilities out, so swapping one for the other is a line of config, and the evals say which wins where.

The world language

The stage manager doesn’t describe the world in prose. It writes operations in a small language, and the world checks every one:

move, place
Someone or something goes to an area, or near, behind, beside, under, on or in something; or a distance away from, or toward, something
give, drop
Changes hands, from wherever it was (part of a stack by quantity: “two of the pennies”)
create
Someone or something new the story just brought in
state, note, forget
States added or removed (open, wet, prone, hidden…); a note worth keeping; a note that’s stopped being true
remove, destroy, break
Leaves the scene; wrecked (what it held falls out); broken (a container spills)
ignite, douse, spill, chill, bleed
The physics: whether it catches, what water does to fire and to burning oil, what a spill meets, ice, blood

WORLD_LANGUAGE, src/world/stage.ts; applyOps, src/world/scene-world.ts

  • It can only name what exists. The model’s output is held to a strict schema whose what and to fields allow only the world’s own ids. It can’t refer to a thing by a made-up name, or to anything that isn’t there.
  • The physics stays consistent. The model is told to use the physics verbs rather than write states by hand: “the physics decides whether it catches: metal and stone only scorch, wet things won't”.
  • Refusals are kept. applyOps never throws. What it can’t do goes in the world’s log as “(not done)”, where the next turn’s GM sees it: “(not done) move: a bench bolted to the floor is fixed where it is”.
  • It records only what happened: “The reply is what happened. Where the model disagrees with it (it may be out of date), the reply wins: put people where the reply has them. Only what has happened, though: not plans, offers, threats, glances or where people's attention goes.” And: “Often nothing changes: an empty list is fine.”
  • It’s measured. A stage-manager eval scores it against 26 labelled exchanges from real play, as precision and recall over atomic changes: positions, hand-overs, states, arrivals and exits. Reasoning at low scored best, at F1 0.82 against 0.68.

The same small language is where scripting starts. A scene’s exit scripts are written against a world API (WorldApi in src/world/dsl.ts: quests, attitudes, memories, items, flags, the journal, a fight to set out). Today they’re recorded rather than applied: the game reads back only the journal and who a fight sets out. The scripting page takes it from there.

Where it still slips

  • The same rule is coded three times. Fire, damage to things and breaking are coded separately for scenes, for the town map and for fights. So people don’t burn outside fights, and a spell’s area ignores walls in a scene but not in a fight. The design is one registry of interaction rules for all three.
  • The stage manager can miss a move, as the thirty feet in step 4 shows; the world eval exists to measure that.
  • The world only ticks while something burns, so a puddle doesn’t dry otherwise.

Limits and honest refusal

Each scene says what it can’t offer, and the GM says no in the story.

  • Limits are written into the scene, each with a reason in the fiction. The hanged clerk has nine, among them: “Getting someone to talk to the dead (a séance, a priest who can call up Prout's ghost): nobody in reach can do it.”

Companions: told, now and held

Between scenes the player can stop for a word with Kell, as with a companion at camp in a cRPG. Her backstory comes out slowly, and the runtime keeps each of her own stories in one of three states.

    Told is told: if it comes up again, even asked for, a line back to it at most ("You know that one."), never the story or its words again.

Fronts and scene boundaries

The world moves when nobody’s looking, and when a scene ends, the story is handed on exactly as play left it.

Fronts

lore/World/Fronts.md is the GM’s list of what’s in motion. Each front is someone or something that wants something: who, what they want, their resources and limits, and a clock of steps. Each step says what sets it off, how it shows, and which scene endings tick it. Below the fronts are “Bills still to come due”: consequences of what the player did, waiting for their moment.

The rules for moving them are in the doc itself. A step ticks “when play has made it true or its time has come, never because it would be dramatic”, nobody acts on what they couldn’t know, and a front changes circumstances inside the scenes but “never adds a scene, a route or an ending”.

Crossing a boundary

When a scene ends, the runtime lists where the story could go: the exit’s next scene, then, if that scene takes something for granted (assumes), the scene it gives way to when play has made that untrue (overtaken). Then three calls run at once, each at Luna’s low reasoning:

  1. the hand-off (handoff): how things stand, exactly as play left them, for the next scene’s GM;
  2. the verdict (boundary): which coming scenes still hold; where the first that holds is out of date (adjustments); its opening rewritten to start where the story is; and the lead, how the player hears where to go;
  3. the world’s turn (fronts): which steps play or time has ticked, which are now meaningless, any new bills, and what of it shows in the next scene.

Each falls back if it fails (a plain hand-off line, no scene skipped, the author’s opening), so a boundary never blocks the story. Here is a real crossing, from the hanged clerk (ended “The case is made”) into the Drowned Rat, in a 31-turn game played in the app.

The budget is five seconds to the words that answer the player. Everything that makes the world remember happens after them, and costs no wait at all.

Why it’s quick:

  • The judgements are small. A decision is one call to a decision model, with every question asked at once.
  • The voice doesn’t reason. Luna as the GM at reasoning low or medium showed no measurable gain over none (81 to 88% of the criteria passed at each level), and medium more than doubled the time to first text, from 1.6 to 3.7 s.
  • Everything else is off the critical path: disclosure runs alongside the decision; the stage manager runs after the reply has been shown; reviews run after the turn.
  • The prompt is ordered for the cache: the long, stable prep comes first.

One exception came later, by the user’s choice. Since 18:03 on 15 Oct a considered turn puts the GM’s review in front of the reply: about 3.5 s, so first text comes at about 5 to 7 s, and the app says the GM is considering. Only the turns the decider flags go there.

Problem reports, and the plain tests

A player who hits a problem presses b on the map, types /report in a scene, or uses the Esc menu. The game saves everything needed in one file: what they said, the screen, the saves, the snapshots, every model call and the errors, with the key taken out. npm run report -- inspect <file> reads it turn by turn, as one turn did; --call <n> shows exactly what a model was told and said; and restore makes it a playable game again. The client is the game’s one UI, carried over from the prototype: the screens, the isometric renderer, the look layer and the glyph font. It holds the rows it subscribes to. It calls moves, and the simulation tells it what happened. It never changes a row itself, never rolls a die, never shows a result the simulation hasn’t committed, and never talks to a model. There’s no client-side prediction. It does run each move’s check, which is pure code shared with the simulation, to offer and grey out what the player can do, as the action menu does today.

The simulation is a SpacetimeDB module and the authority on everything that happens. Its functions are the moves:

  • a move with no model call is a reducer: one transaction, deterministic, with no outside world. Walking, a Fireball on the map, a rest and a hand-off are reducers;
  • a move that needs the AI is a procedure: it reads in one transaction, calls the AI API over HTTP with no transaction open, and commits what came back in another, after checking that nothing it relied on has moved;
  • views give each player what’s theirs: their seat, their spend, the names they’ve heard. Clients subscribe to tables and views, and every change is pushed to them;
  • schedule tables run the jobs (memory reviews, the co-GM, scene boundaries) and the world’s clock.

The rules engine (dnd-srd-engine) and the world’s interaction rules run inside it, so every die is rolled in one place, from the game’s seed.

The AI API is an HTTP service that does the model work and keeps the words. It holds the GM pipeline and its deciders (Luna’s decision mode for the director, Jev for disclosure and the reviews’ attention), the co-GM, the stage manager, the memory reviews, the docs service, the prompts and the call logs. It’s self-contained: it never reads the simulation’s tables. Every request carries the working set it needs (the scene’s state, the transcript, the place’s world, who’s present), and every answer comes back as data: decisions, text, world operations. It writes to the simulation in one place only: the text of a reply as it’s written, through the streamReply reducer.

The campaign is data: a folder or a git repo, below. OpenRouter is the only model provider, and only the AI API calls it. Its Responses API serves Luna; its Decisions API serves Luna’s decision mode and Jev, the fast judgements, about 0.3 s each. The key lives in the AI API and nowhere else.

Why it’s split this way

Each line is drawn where something can’t cross it: a transaction can’t wait for a model, and a document doesn’t belong in a row.

  • A transaction can’t wait for a model. A reducer finishes in milliseconds and can’t call out. A model call takes 0.3 to 20 seconds and sometimes fails. So every move that needs the AI is cut at the model call: the deterministic work happens in transactions, and the thinking happens between them, with nothing locked.
  • The simulation owns the game, and the AI API owns the words. Anything the next move needs is a row in the simulation. Anything that’s a document (lore, memories, fronts, prompts, logs) belongs to the AI API. The AI API can restart or scale freely, and an eval can call it with a recorded working set and nothing else.
  • The GM always gets every fact. Each request carries the whole working set, so the GM never has to guess at what it wasn’t shown. Secrets, held stories and what each person has been told travel with their status: told, now or held.
  • One authority for dice and rules. The rules engine and the interaction rules run only in the simulation, from the game’s seed. So the map, the world and the GM never disagree, and a game can be replayed.
  • Clients only read rows and call moves. The app, the QA console, the zoo’s tour and a second player’s terminal all play through the same moves and see the same rows.
  • Secrets aren’t a security concern. The content is public and the game isn’t competitive. The GM’s tables are private to save bandwidth and spare players spoilers; cheating isn’t the worry.

One module, two hosts

The module’s code is written against a small interface, so the same moves run on SpacetimeDB in production and in one process everywhere else.

The interface is four things: tables, transactions, the dice and an AI client. It has two hosts:

  • the SpacetimeDB host, in production: reducers, procedures, views and schedule tables for real, with the AI API over HTTP;
  • the local host: the same code over in-memory tables in one process, with the AI API called in-process through the same request and response types, serialised as JSON so nothing is shared by accident. A transaction is a copy-on-write over the tables, committed with a revision check, and subscriptions are row diffs pushed to clients in the same process, or over a WebSocket.

For now, everything runs in one process, with a boundary between the two, and that’s the local host. It stays after the SpacetimeDB host arrives. The terminal game, the static preview (in a browser worker, with the player’s own key), the QA console, the zoo’s tour and the tests all run on it, so the GitHub Pages previews still need no server.

How the code is put together

The user’s brief for production (docs/code.md) asks for single responsibilities, dependency injection without a framework, and code that reads easily in review. The design turns that into a few rules:

  • Config is owned by each part, and assembled into one JSON. A kind field picks a strategy, so the approaches become presets. Secrets are referenced, never stored, and nothing reads config or process.env when it’s imported.
  • Services are a typed record. Each part gets only what it uses, rather than a dynamic services.add that drifts into a service locator.
  • Exported and orchestration functions read as flat steps that call helpers, so a package’s shape shows at a glance. The eslint rules in the brief (max-depth 2, max-nested-callbacks 2, complexity 10, cognitive complexity 12) are guidance, not CI.

Every row belongs to one game, through a game_id or the id of something in the game, except the campaign’s rows and the host’s own.

A public table can be subscribed to by clients. A private one is read only by the module: the GM’s bookkeeping, the dice, the rules engine’s state. Stores behind interfaces

Every store is an interface, so a test, the terminal, the static build and a hosted build can each pick their own.

The moves see their tables only through Rows and Tx (the Move interface has them in code), so the same moves run over SpacetimeDB’s tables or the local host’s in-memory ones. Around them, the design puts each store behind an interface. Each has memory, file, IndexedDB and Firestore implementations, chosen by config and checked by one set of contract tests:

export interface GameStore {
  load(game: GameId): Promise<WorkingSet>;
  commit(game: GameId, change: Commit): Promise<Revisions>;   // all or nothing; fails on a stale revision
}
export interface LeaseStore { acquire(key: string, holder: string, ms: number): Promise<Lease | undefined>; release(lease: Lease): Promise<void> }
export interface JobQueue { enqueue(job: Job): Promise<void> }                  // inline | worker | Cloud Tasks

export interface AgentLog { call(record: CallRecord): void }                  // file | console | Cloud Logging
  • Stores are async at the edge, and a turn works on a synchronous working set. A turn loads its working set (the story, the scene, the world, the transcript’s tail, the GM’s state and the lore, with their revisions), changes it in memory, and commits once. A failed turn discards its working set. The domain code stays synchronous; only the turn’s host awaits a store.
  • With SpacetimeDB, the game store is the module’s tables. A lease is a row (a scene’s turn_id; the job runner’s lease per game and kind), and the queue is the job schedule table. The AI API keeps its own stores: the docs, the call logs, the answers by key.
  • The model client has three versions: OpenRouter; a fake, scripted by operation; and a replay that serves a game’s logged calls back in order, so a replayed game shows any prompt that drifted.

If it ever goes on Firestore

Firebase is only a possibility: nothing is built on it yet. It would be a third host for the same module, as the local host is a second.

The host would be the Tx interface over Firestore, with the procedures’ host on Cloud Run. The last column of every table above says where its rows would go. The mapping holds, with these changes:

  • A game’s private tables go in collections whose names start with gm, which the security rules let no client read; the host’s own (seat, budget, the campaign’s) go where only the server reads. Firestore secures whole documents, so anything one player mustn’t read can’t share a document with what they may. A table read through a view keeps its own collection, and each player reads only their own documents.
  • The component tables fold into one document per entity, a field per component. Firestore reads, writes, listens and bills by the document, so a collection per component would multiply every read. A component change becomes a field update in the move’s batch.
  • Event tables become collections with a TTL field. Listeners animate from them, and Firestore deletes them within a day.
  • A move becomes a function on Cloud Run (Cloud Functions for Firebase stop at Node 22, and the code needs Node 26). A reducer becomes a short Firestore transaction. A procedure becomes a handler that leases the scene, calls the AI API with no transaction open, and commits with the revision check. A Firestore transaction is never held across a model call: the server SDKs lock pessimistically, and a retry would bill the model again.
  • The schedule table becomes Cloud Tasks, each task idempotent by its key.
  • reply_draft becomes a document rewritten about four times a second with the whole text so far, so a missed update loses nothing.
  • Clients write nothing. Every move is a call to the server.
  • Sizes need watching. The rules engine’s log was 29 KB after 14 turns. A snapshot every 50 events keeps each document far under the 1 MiB limit.

Firebase Auth with an allowlist would gate who plays, and the OpenRouter key would live in Secret Manager. Google Cloud would add about $0.0002 to $0.0009 a turn for Firestore, compute and logs; all in, a turn would be about $0.007 to $0.009, roughly 90% of it model calls.

The Move interface

Each move is one module with up to four phases, and the same code runs on both hosts.

check
Pure. May this actor make this move now? It reads only rows the player’s client has too (public tables and the player’s views), so the client runs it as well, to offer and grey out actions.
resolve
Deterministic, in a transaction. It records the move, rolls the dice, changes the world, and returns done or a plan for the AI.
think
The AI, outside any transaction. It says what to ask the AI API, and the host sends it with nothing locked.
commit
Deterministic, in a transaction. It checks the plan again against the latest revisions, applies the AI’s answer, and returns done, or another plan to think about.
// sim/moves/move.ts

/** Something a player, or the GM, asks to do. One module per move; the same code on both hosts. */
export interface Move<Args, Plan = never> {
  readonly name: string;

  /** Pure: may this actor make this move now? Reads only rows the client has too, so the client can run it. */
  check(rows: Rows, actor: Actor, args: Args): Refusal | undefined;

  /** Deterministic, inside a transaction: record the move, roll the dice, change the world. */
  resolve(tx: Tx, actor: Actor, args: Args): Next<Plan>;

  /** The AI, outside any transaction: the request to send the AI API next. Only moves that think have it. */
  think?(plan: Plan): AiCall;

  /** Deterministic, inside a transaction: re-check against the latest revisions, then apply the AI's answer. */
  commit?(tx: Tx, plan: Plan, answer: AiAnswer): Next<Plan>;
}

/** Done, or a plan to think about. The plan is saved in `move_plan`, so any process can carry it on. */
export type Next<Plan> = { done: true } | { done: false; plan: Plan };

/** Why not, in the game's own words: "(Fireball (3rd-level slot): no clear line to there.)" */
export interface Refusal { code: RefusalCode; text: string }

/** What resolve and commit work on: the tables, and the services that write them. */
export interface Tx extends Rows {
  readonly now: Timestamp;
  readonly dice: Dice;          // the game's seeded stream, kept in the `dice` row and advanced in this transaction
  readonly world: WorldStore;   // entities and components; commands; the interaction rules, run until nothing changes
  readonly rules: RulesBridge;  // the D&D engine: checks, saves, spells, blows, rests
  write: TableWriter;           // insert, update, delete
  emit(event: WorldEvent | RulesEvent | Notice): void;
  schedule(job: JobSpec): void; // a `move_plan` row and a `job` row: runJob picks it up at once
}

A move with only check and resolve is a reducer and nothing more. A move that thinks is a reducer and then a procedure. The reducer checks it, records it, saves its plan and schedules runJob, the one procedure that does the thinking. runJob thinks and commits until the move is done, and commit can hand back another plan: a line in a scene thinks three times (decide, reply, settle) and commits after each.

A reducer starts every move, so:

  • every move is acknowledged the same way, by a commit within milliseconds;
  • a turn’s plan is saved before any thinking starts, and each commit saves the next one;
  • a turn carries on if its player’s connection drops, or if the host restarts mid-turn: reapTurns, a scheduled reducer, finds a turn that hasn’t moved for a minute and schedules it again with the same keys.

The hosts run them

On SpacetimeDB a move becomes a reducer, and every move that thinks runs in one procedure:

// sim/hosts/spacetime.ts: the SpacetimeDB host

/** A move as a reducer: check and resolve in one transaction. A plan, if any, goes to runJob. */
export function reducerMove<A>(move: Move<A, unknown>, params: ParamsOf<A>) {
  return spacetimedb.reducer(params, (ctx, args) => {
    const tx = txOf(ctx);
    const actor = actorOf(tx, ctx.sender);

    const refusal = move.check(tx, actor, args);
    if (refusal) throw new SenderError(JSON.stringify(refusal));   // nothing written: the caller's promise rejects

    const next = move.resolve(tx, actor, args);
    if (!next.done) tx.schedule({ move: move.name, plan: next.plan });
  });
}

/** Every move that thinks runs here: think with no transaction open, commit inside one, until it's done. */
export const runJob = spacetimedb.procedure({ onSchedule: job }, { arg: job.rowType }, t.unit(), (ctx, { arg }) => {
  const move = MOVES[arg.move];
  let plan = loadPlan(ctx, arg.plan_id);                                  // from move_plan, in a short transaction

  for (;;) {
    const answer = callAi(ctx, move.think!(plan));                        // ctx.http.fetch: synchronous, nothing locked
    const next = ctx.withTx(tx => move.commit!(txOf(tx), plan, answer));  // saves the next plan; may run more than once
    if (next.done) return;
    plan = next.plan;
  }
});

callAi posts to the AI API with the request’s idempotency key and a timeout, and retries a 429 or a 5xx with backoff. SpacetimeDB caps a procedure’s HTTP request at 180 s. ctx.withTx may run its function more than once, so commit is a pure function of the rows, the plan and the answer: the dice are rows, and nothing outside the transaction is touched.

The local host runs the same Move objects. A transaction is a copy-on-write over in-memory tables, committed with a revision check. think is awaited on the in-process AI API. Subscriptions are row diffs pushed to clients in the same process, or over a WebSocket.

Concurrency and BG3-style control

Reducers don’t interleave, a scene has one turn in flight, and the player who starts a scene controls it until they hand it off.

Two players in the granary yard: Wren, a wizard, walked in first, and Tamsin, a rogue, is there too. Step through what happens when both want to talk, and Cob won’t talk to a wizard.

The rules, in full

  • Reducers don’t interleave. Each runs in its own isolated transaction. SpacetimeDB may run one again if it finds a conflict, which is safe because a reducer is a pure function of the rows and its arguments (the dice are rows). Two players walking, or one walking while another casts, happen one after the other.
  • One turn in flight per scene. say and deed take the scene’s lease, scene.turn_id. A second line while the GM is deciding or replying is refused (turn_in_flight). A line sent once the reply is final, while the world catches up, is kept as a queued turn and starts the moment the settle commits. The player can answer as soon as they’ve read the reply.
  • The player who starts a scene controls it (scene.controller_id) until they hand it off. Only the controller’s lines go to the GM. Anyone else whose character is in the scene’s place is a watcher: they see the conversation and the reply as it’s written, and can ask for the lead (requestControl).
  • One stage at most. on_stage is keyed by entity, so a person or a thing is in one live scene at most. A game can have several live scenes at once, as a BG3 party splits up: Tamsin in the granary yard while Wren talks with Kell on the river stairs. A move at someone on another stage is refused: “(Kell is in a scene on the river stairs.)”
  • A live scene’s place belongs to the scene. Walking into it makes you a watcher. Casting into it from outside is refused for now; later, a watcher’s act could break into a scene, as it can in BG3.
  • The revision check. A plan records the scene’s and the place’s rev as it last saw them (move_plan.seen), and every commit reads them again. If the scene’s turn is no longer this one (the scene was ended, or the turn cancelled), the commit records any reply already shown, and stops. If the place has moved on, each world operation is checked again on the latest rows, and what no longer applies is dropped and logged as a problem for the co-GM. Text already shown is never taken back: v2 dropped speculative replies because players saw replies withdrawn.
  • Hand-offs land between turns. One accepted during a turn in flight passes control when that turn’s last commit lands.
  • Jobs commit only while they still apply. The co-GM’s notes are dropped once the scene has moved on to another. A memory review writes only the AI API’s documents. A boundary runs once for each scene’s end, by its key.
  • Disconnects. onDisconnect marks the player offline. A scheduled releaseControl two minutes later passes the lead to the watcher who has been there longest, or pauses the scene until someone comes back.
  • The world’s clock. In a scene, each turn is one round of the place’s time: what the last reply left hanging (fire spreading, a spell running out, a blow) lands first, in the turn’s resolve. On the map, tickPlace runs a round every 6 seconds in a place that’s active, while a player is there; when someone comes back, it catches up, up to ten rounds, then each component settles (fires burn out, puddles dry). In a fight, a round is a round. This ends the prototype’s “world time only passes while something burns”.

A client connects to the simulation with SpacetimeDB’s TypeScript SDK, calls moves as reducers, and subscribes to rows. In the game, its code goes through a small Connection interface, with one implementation over the SDK and one over the local host. The shapes are the same on both.

try {

The acknowledgement is the promise resolving. It resolves when the move’s first transaction commits, and the rows that transaction changed reach every subscriber in the same update. The scripting API

One language, three writers: a feature with no engine change, and what to do when data isn’t enough.

In short for nowThis page has the target and where we are. The full page, with the language’s operations, selectors and events, a skep of bees in full, and when data isn’t enough, comes in a later milestone. Kell has it down as a theory, and she can’t arrest a theory.

1

The target, in short

A campaign’s own features are data, in one language the engine interprets. A new feature is a module and a zoo exhibit, with no change to the engine.

Components, interaction rules, moves, and what happens at a scene’s exits are all written in one language. It grows out of two things that exist already: the world language the stage manager writes today (the bridge shows it at work), and the interaction rules in docs/design/productionise.md. Three writers share it:

  • the stage manager writes world operations after each reply, as now, naming only what exists;
  • a campaign’s authors write rules, moves and exits’ effects, by hand or in the scene editor, where a model can draft what happens when the story crosses an edge;
  • the rules themselves write operations when they fire.

Operations come in three kinds. The world’s are move, ignite, spill, break and the rest, as the stage manager writes them today. The story’s are quest, flag, attitude, remember and journal. The rules’ own add and drop components, deal damage, spawn a prefab, roll a save, and wait (after). Selectors say what an operation acts on: an entity’s key (elm), a variable ($self, $target), or a query (all has:flammable within:5:$self).

One chain, step by step

  1. An operation reaches the gate. The Fireball’s blast sets the hoist beam alight: the rules write burning onto it.
  2. The gate checks it against the world, as it checks the stage manager’s operations. The beam is there, so the change lands.
  3. The round turns, and the fire rule runs for everything burning: a burning thing sets alight what’s flammable within 5 ft.
  4. Its operation goes back through the same gate. The hoist rope is 5 ft from the beam, and it catches.
  5. The change lands in the world’s log with its cause, “the hoist rope catches fire (the hoist beam burning, 5 ft away)”, and the GM is told before the next line is decided.

Ice melts near fire

In the prototype, ice melting near fire touches about eight places: the physics, the physics prose for the models, the world-op schema, the stage manager’s language, the look director, the map’s decay, and the fights, which have no ice at all. In the language it’s one rule:

- id: ice-melts
  each: { has: [surface], near: "has:burning within:5:$self" }
  if: { surface.stuff: ice }
  then:
    - { set: { what: $self, surface.stuff: water } }
  words: { gm: "Ice beside a fire melts to water." }

Rules run in the transaction that caused them, until nothing changes, and a chain stops at eight steps. They roll from the game’s seeded stream, so a game replays. The campaign tool checks every rule at install and runs every exhibit, and a campaign that fails doesn’t install. Each component’s words join what the GM is told, so the physics the models read is generated from the rules. For loops, arithmetic and anything the conditions can’t say, the same API is there in TypeScript.

The spike, first

The SpacetimeDB documentation doesn’t settle five things the module depends on:

  1. Does a procedure waiting on HTTP hold up other reducers? If it does, the AI work moves out of procedures, behind the same Move interface.
  2. How long does a reducer take with the rules engine in it?
  3. Is everything the engine does deterministic inside a module?
  4. Does streamReply stay smooth at five posts a second, with four subscribers?
  5. Do the longest jobs fit? A memory review has taken 105 s, against the 180 s cap on a procedure’s request.

  • Prompt drift through the refactors: the replay names any prompt that changed for the same game.

  • Cost: with the background jobs, a turn costs under a cent, and two hours for four players about $1. The caps come before they’re needed.
  • Sizes: the rules engine’s log and the transcript, per game and per turn.
  • The world track changing behaviour: the zoo’s world expectations are the regression suite.
