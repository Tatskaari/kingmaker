# Kingmaker: architecture

The way in for reviewing the game. It says what the parts are and how they connect, where state lives and how a change is checked, and links to each part's own doc for the detail. The [README](README.md) pitches the game and [docs/running.md](docs/running.md) says what you can play and how to run it; its [rules](docs/running.md#the-rules) are the ones every part keeps.

## The parts

```mermaid
flowchart LR
  client["client/<br/>the screens (OpenTUI)"]
  sim[("simulation/<br/>a SpacetimeDB module:<br/>the authority")]
  ai["ai/<br/>the AI service:<br/>stateless HTTP"]
  router(["OpenRouter"])
  campaign[/"campaigns/caerwyn/<br/>the campaign, as data"/]
  client -- "moves (reducers)" --> sim
  sim -- "rows" --> client
  sim -- "thinks, from a scheduled procedure,<br/>each with the working set it needs" --> ai
  ai -- "answers by key; the GM's words<br/>streamed through a reducer" --> sim
  ai --> router
  campaign -. "installed in both" .-> sim
  campaign -.-> ai
```

- **The client** ([client/](client/)) is the game's screens on OpenTUI, in a terminal: the title, character creation, the sheet, the town's map and its action menu, the scene with its place drawn beside the talk, a fight played out a move at a time on its map ([client/fight/](client/fight/): the playback of its moments, and the action menu aimed on the board; [docs/combat-design.md](docs/combat-design.md)), the notebook and The End, and over any of them a report of a problem ([client/report/](client/report/): the question, the screen kept as it was, the report filed with its host); and the game's sound ([client/sound/](client/sound/), [docs/sound-design.md](docs/sound-design.md): what the menus, the talk, the dice, spells, blows, the world and a fight sound like, and the music for each screen, as words for a sound engine made of nothing but parts, which the page plays). It reads rows and sends moves (and asks its game's host for the game, for a report), and never talks to the AI service. Its bindings ([client/module_bindings](client/module_bindings/)) are generated from the module. Headless, the same client is the QA console (`npm run play`).
- **The simulation** ([simulation/](simulation/)) is the authority on everything that happens: every table, reducer, procedure and view ([schema.ts](simulation/src/schema.ts), [index.ts](simulation/src/index.ts)), the moves as plain functions over the tables, the job loop that asks the AI service ([jobs.ts](simulation/src/jobs.ts)), the GM's bookkeeping, the rules engine pinned to the game's dice, the story between scenes and the town, and a fight on a map a turn at a time ([fight/](simulation/src/fight/): the prototype's rules of the board and its AI on the engine, the other side's turns played one at a time by a scheduled reducer, each thing anyone does written as a moment for a screen to animate; started from the zoo for now, [zoo/](simulation/src/zoo/): a visit to its combat ring, set out from the zoo's own files ([shared/zoo/exhibits.ts](shared/zoo/exhibits.ts)), or one of the arena's rings ([shared/zoo/rings.ts](shared/zoo/rings.ts)); [docs/combat-design.md](docs/combat-design.md)). It's deterministic, and every move also runs on a memory host in the tests. Blueprint: [docs/v0-design.md](docs/v0-design.md) §3, §4 and §6.
- **The AI service** ([ai/](ai/README.md)) does all the model work and keeps the words: the GM (the two-part GM that plays the story's scenes and the talks between them), character creation's builds and backstories, the docs service (the lore, each game's copy of it, and the GM's notes on each person), the prompts and the model client. It holds nothing between requests: each carries what it needs, and each answer is stored by its key before it's sent, so a retry is answered from the store.
- **Shared code** ([shared/](shared/)) is what the others run alike: the protocol between the simulation and the AI service, the scene graph and its loader, the world and its rows, the rules code, the map code. ES2021, no Node, no packages, since it runs in the module.
- **The hosts** ([hosts/](hosts/)) are the composition roots, the only code that reads the environment or argv: the AI service's process, the terminal client and the headless one, the dev stack that brings SpacetimeDB and the AI service up on one machine ([hosts/dev/README.md](hosts/dev/README.md)), the campaign tool, the end-to-end and live runs, and the page's workers.
- **The game in a browser** ([web/](web/README.md), [hosts/web/](hosts/web/), [docs/browser-design.md](docs/browser-design.md)) needs no server. A client worker runs the client on a JS stand-in for OpenTUI ([web/tui/](web/tui/)) drawn into xterm.js; a server worker runs the simulation on its memory host and the AI service beside it, both kept in IndexedDB ([web/server/](web/server/)); the two speak the wire in [shared/protocol/port.ts](shared/protocol/port.ts). The model calls go to OpenRouter with the player's own key, or the fake GM plays. The game's sound is the page's: the client worker says what to play, and the sound engine makes it on the browser's audio thread ([web/page/sound.ts](web/page/sound.ts), [sound-worklet.ts](web/page/sound-worklet.ts)).
- **Campaigns are data** ([campaigns/](campaigns/README.md)): Caerwyn, the story, and the zoo ([campaigns/zoo/](campaigns/zoo/README.md), M6), the game's features as exhibits in the same format, which the title, `npm run zoo`, the page's `?zoo` and headless play open (its exhibits are its scenario's `exhibits`, held to their files by [shared/zoo/exhibits.ts](shared/zoo/exhibits.ts); no GM plays it, so it's installed in the simulation alone). Each has the scenario (`<id>.kmscenario`), each scene as one `.kmscene` file ([docs/scene-format.md](docs/scene-format.md)), the maps (`.kmmap`) and places (`.kmplace`) of the scenario format ([docs/scenario-format.md](docs/scenario-format.md)), all of them the Obsidian plugin's format too, the looks and ready-made builds, and the lore. [shared/scene/document.ts](shared/scene/document.ts) is the scene format, [scenario.ts](shared/scene/scenario.ts) the scenario's, maps' and places' (it makes the shapes the game kept before them, [files.ts](shared/scene/files.ts)'s and the map's), [load.ts](shared/scene/load.ts) makes the runtime's Scene from a file and [beats.ts](shared/scene/beats.ts) says where a scene is (reached, its stage, its open routes, a route taken), the same code on both sides; [rules.ts](shared/scene/rules.ts) has the format's rules for a scene and [scenario-rules.ts](shared/scene/scenario-rules.ts) the scenario's, maps' and places', which `npm run campaign -- check` holds a folder to (with the rest of the campaign's) and the authoring plugin runs as a file is edited, and installing it puts it in both services.
- **The site** ([web/site/](web/site/), [hosts/web/build-site.ts](hosts/web/build-site.ts)): the pitch and the roadmap in front of the game's page at `play/`, published by GitHub Pages, with a preview of each PR.
- **Reports of a problem** ([qa/report/](qa/report/), [hosts/report.ts](hosts/report.ts), M5): a player's report read (`npm run report -- inspect`: the summary, a turn, a call, a table) and its game restored into a local stack for a session to carry on (`restore`: the module's `restore_game`, the database owner's, and the AI service's `PUT /v1/games/{game}/docs`); the report itself is the client's (client/report) and its host's (`report_game`, the game's owner's procedure: every table's rows of the game, and the AI service's calls and docs for it).
- **The GM loop** ([qa/loop/](qa/loop/README.md), [hosts/loop.ts](hosts/loop.ts)): QA rounds on the game, as the prototype ran them. Blind persona testers play scenes on a dev stack of the loop's own through the headless client's verbs, each game its own session, a later scene reached through every real boundary before it (each scene on the way ended for QA as the stack's owner). Blind reviewers judge each game from a pack of the scene's prep as the AI service's loader gives it, and a report shows the arms, the endings, the triaged findings and each turn's model calls from the stack's call log. Run by the `kingmaker-gm-loop` skill ([.claude/skills/](.claude/skills/kingmaker-gm-loop/SKILL.md)) and its workflow.
- **The tools beside it** ([tools/](tools/)): the Obsidian authoring plugin ([tools/authoring/](tools/authoring/README.md), its own package), whose vault is the campaign folder: it edits the campaign's files as they are (the scenes, the scenario as the story's flow drawn from the files that own it, the maps painted in their legends' characters with their regions, exits and people, and the places, laid on their maps or on their own grids), holding each to the format's rules as it's written and previewing maps with the game's renderer ([client/map/render.ts](client/map/render.ts)); the Kingmaker Glyphs font's build ([tools/glyphs/](tools/glyphs/README.md)); and the SRD spell texts' build ([tools/srd-spells/](tools/srd-spells/build.py)).

## A turn

A line said in a scene of the story, as [docs/two-part-design.md](docs/two-part-design.md) tells it in full (the plumbing is [docs/v0-design.md](docs/v0-design.md) §6's; a talk with Kell between scenes plays the same steps, with no world and no dice, [docs/town-design.md](docs/town-design.md) §3.6):

1. The client calls the `say` reducer. The simulation writes the line, settles what the rules owe first (a fire burning on, a spell running out, and an act from the map's menu, which opens a waiting scene as its first turn), reads the line for a spell, a blow or a class feature by its words ([shared/rules/acting.ts](shared/rules/acting.ts), no model), and starts the turn's job.
2. Each step is a POST to the AI service from a scheduled procedure, with the working set it needs, keyed `<game>:s<scene>:t<turn>:<step>`: for a line that might be an act, first `act` (what the rules resolve of it, which the simulation resolves on the world before the GM says a word, its dice lines first) and, for violence, `reactions` (how everyone who saw it takes it); then `reply` (the two-part GM's mouthpiece: its words streamed to the turn's draft as they're written, and a check when a roll should settle something, which the simulation rolls from the game's `dice` row through the rules engine, writing the dice line and the outcome that came up), then `settle` (the stage manager keeping the world in step, beside the co-GM, which sets each person's role for the next reply and moves the scene along its routes; the simulation takes each move again with the same code, [shared/scene/beats.ts](shared/scene/beats.ts)). The simulation commits each answer.
3. Beside the turn, the suggested lines; after it, in the background, the memory reviews (`remember`). A route to an ending leaves the scene closing, and the next line's reply winds it down; at a scene's end, the `boundary` moves the story on.

## Where state lives

| Where | What |
|---|---|
| SpacetimeDB's tables | Everything that happens: games, scenes and turns, the transcript, the world's rows, the dice, the GM's bookkeeping, the jobs in flight. The authority |
| The AI service's stores | The answers by key, each game's call log, memory reviews and copy of the lore (read back for a report of a problem), the cost ledger, the installed campaigns: a folder (`runs/dev/ai` under the dev stack), or memory kept in IndexedDB in a page |
| `runs/reports/`, the browser's downloads | Reports of a problem: one gzipped JSON file each, the game's rows and the AI service's own of it among what's in it, every key out ([docs/running.md](docs/running.md#reporting-a-problem)) |
| The repo | The campaign, the prompts, the vendored rules engine and SRD texts |
| `runs/`, `dist/` | Run and build output, never committed |

## Checking a change

| Command | What it checks |
|---|---|
| `npm run check` | The type checks, the unit tests and the client's screens, offline (about 45 s) |
| `npm run e2e`, `npm run arc` | End to end on a real SpacetimeDB, the AI service on the fake model |
| `npm run build:site`, `npm run web:check` | The site, then the page played in headless Chromium on the fake GM |
| `npm run campaign -- check campaigns/caerwyn` | The campaign folder is fit to install |
| `npm run live -- --script <name>` | A scripted run on real models, recorded in [docs/live/](docs/live/) |
| `npm run loop -- <command>` | A QA round: blind persona testers and reviewers on real models, triaged and reported ([qa/loop/README.md](qa/loop/README.md)) |
| `npm run report -- inspect <file>` | A player's report of a problem, read: the summary, then a turn, a call or a table in full; `restore` makes its game a new game in a local stack ([docs/guide/testing.md](docs/guide/testing.md#investigating-a-players-report-for-claude)) |

CI runs [check.yml](.github/workflows/check.yml) (the checks, e2e, the browser and the AI service's image) on every PR, [preview.yml](.github/workflows/preview.yml) publishes each PR's site, and [pages.yml](.github/workflows/pages.yml) publishes main's. The authoring plugin has its own checks ([tools/authoring/README.md](tools/authoring/README.md#checks)), which check.yml's `authoring` job runs.
